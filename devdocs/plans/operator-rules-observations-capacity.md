# 규칙 현황, 파일·네트워크 관측, 저장·전송 측정

## 목적과 순서

1. 호스트에서 사용하는 14개 규칙의 제목, 버전, 정책과 센서 상태를 같은 정의에서 조회한다. 두 로컬 설정을 같은 정규화 이벤트로 비교해 변경 영향을 확인한다.
2. 정상 배포·업로드·외부 API 호출 표본에서 실제 쓰기와 TCP 연결 시도의 결과, 서비스 귀속을 확인한다. 서비스별 보호 경로의 쓰기는 경보 도입 전 검토 후보로 표시한다.
3. 이벤트를 추가 수집하며 늘어나는 저장량, 대기열, 손실과 중앙 ACK 복구 시간을 측정한다.

## 인터페이스와 데이터 흐름

- 규칙 카탈로그는 실행 중인 탐지 정책의 스냅샷과 선택된 센서의 수신 상태를 결합한다. CLI, 패널, 이력 제목 검색은 같은 규칙 정의를 사용한다. 오프라인 비교는 한 호스트·부팅의 비식별 JSONL을 현재·후보 설정으로 각각 재생하고 규칙별 변화와 서비스만 출력한다.
- 파일·네트워크 표본은 이미 로컬 DB에 보존된 이벤트에서 결과와 서비스 귀속을 조회한다. 파일은 실제 양수 반환, 0바이트, 실패, 결과 불명을 구분한다. TCP 연결 시작과 완료는 구분하며 센서가 확인한 시작 결과만 표시한다. 허용된 업로드·캐시 경로는 같은 서비스의 보호 경로 안에서도 제외할 수 있다.
- 저장 통계는 UTC 일자별로 최초 커밋된 관측을 센다. 기존 전송 대기열을 마이그레이션 시 한 번 집계하고 이후 추가·ACK와 같은 트랜잭션에서 수량과 바이트를 갱신한다. 재전송, 손실, 최초 복구 ACK와 완전히 비운 시각을 구분한다. 기존 상태 API와 중앙 heartbeat의 capability details 계약을 재사용한다.

## 실패와 호환성

관측이 없거나 센서가 미검증인 경우 그대로 표시한다. 기존 이벤트와 미등록 호스트도 조회할 수 있어야 한다. 실제 대응과 정책 서명·배포는 기존 관리 경로가 맡는다. 오프라인 비교는 호스트 센서, 운영 DB와 분리한다. 단절 중에는 대기 한도가 적용되고, 이전 DB의 과거 일일 통계는 계측 시작 시점에 따라 해석한다.

## 대용량 기존 DB에서의 기동

스키마 5는 기존 이벤트 종류·시각 인덱스로 파일과 TCP 이벤트만 읽어 서비스 조회표를 채운다. 이후 해당 이벤트를 삽입하는 트랜잭션이 조회표를 갱신하고, 보존 기한으로 이벤트를 삭제하면 참조 행도 함께 삭제된다.

첫 운영 배포에서 설치·수집 검증이 끝난 뒤 입력 큐 대기가 늘어났다. 기존 프로세스 정리 SQL의 실행 계획에서 경보·이벤트 참조 확인 시 테이블 전체를 읽을 수 있음을 확인했다. RPM 30은 프로세스를 한 페이지에 최대 250개 확인하고 참조 인덱스를 사용한다. 페이지 커서를 삭제와 같은 트랜잭션에 저장해 재시작 후에도 작업을 이어간다. 배포 검증은 설치 결과와 함께 기동 30초 후 시작되는 정리 작업 동안 큐 깊이, 입력 드롭, 최근 이벤트와 중앙 ACK를 확인한다.

RPM 30을 적용한 대용량 호스트에서는 큐 드롭이 멈췄으나 재시작 시 로컬 API가 약 65초 후 준비돼 업데이터의 60초 기한을 넘겼다. RPM 31은 마지막 이벤트 순번을 복원할 때 기존 부팅·스트림·순번 인덱스의 조건을 명시한다. 현재 부팅·스트림의 양수 순번과 보존 기한 정리 전 기록된 상한 중 큰 값을 사용한다. 추가 스키마 변경 없이 이전 DB에서도 같은 순번을 복원한다.

## 검증

규칙별 제목 검색, 정책 전환, 센서 상태, 동일 입력 재생과 잘못된 입력을 검사한다. 파일·네트워크 테스트는 정상 표본과 경로 경계, 다른 서비스, 실패·미확인 결과를 포함한다. 저장·전송 테스트는 기존 DB 업그레이드, 중복 입력, ACK·한도 초과, 끊긴 연결의 복구와 대기열 소진을 검증한다. 마지막에 전체 빌드·테스트와 기존 탐지 시나리오를 실행한다. 실제 배포와 운영 표본 측정은 별도로 구분한다.

## 구현 결과와 격리 시험

- `sentinel rules`와 시스템 패널에서 14개 규칙을 조회하고 같은 한국어 제목으로 이력을 검색한다. `sentinel rules compare`는 한 호스트·부팅의 표본으로 두 로컬 YAML의 경보 추가·감소·변경과 영향을 받은 서비스를 표시한다.
- `sentinel observations`와 패널 실행 이력에서 이벤트에 저장한 서비스를 기준으로 조회한다. 정규화 전 Tetragon 표본을 사용해 양수·0·음수·결과 없음, 정상 배포·업로드·캐시와 외부 API의 TCP 시작 결과, PID 재사용, 재수신과 역순 도착을 확인했다. 파일·TCP 표본으로 생성된 경보는 0건이었다.
- `sentinel capacity`와 시스템 패널에서 SQLite 마이그레이션 이후의 오늘·어제 UTC 신규 이벤트 JSON 바이트, DB·WAL·가용 공간, 큐 수위·저장 지연, 전송 대기량·손실을 확인한다. 에이전트는 마지막 단절 구간의 첫 ACK, 대기열 소진과 손실을 DB에 보존한다. 보존 기간이 지난 이벤트의 조사량을 제한하며, 제한에 도달하면 적체량을 하한으로 표시한다.
- 독립 중앙 바이너리와 에이전트 두 개를 임시 DB·인증서로 구동했다. 중앙 중단 중 각 에이전트에 65건이 쌓였다. 한 실행에서 A는 77,909바이트, B는 77,882바이트를 대기열에 보존했다. 첫 전송 실패부터 첫 ACK와 전체 소진까지 각각 A는 2.021초·2.024초, B는 2.020초·2.022초였다. 두 호스트 모두 구간 손실이 0건이었고 재전송 후 중앙 이력과 다음 heartbeat의 복구 시각을 확인했다. 이 수치는 루프백 시험 결과다.
- 전체 `make verify`에서 소스·형식 검사, 설치·패키징 시험, Go vet·race, 정적 바이너리 4개 빌드와 기존 탐지 재생 20건을 통과했다. 설치 마법사의 모의 터미널 신호 시험은 한 차례 시간 초과가 있었고 터미널을 할당한 전체 재실행에서 통과했다. 새 바이너리로 임시 데몬에 배포·업로드·TCP 표본 3건을 재생해 CLI에서 규칙 14개, 검토 후보 1건, 경보 0건, 당일 저장 3건을 확인했다.

## 운영 업데이트 결과

EL9 첫 호스트에서 RPM 29의 기동 후 입력 큐 시간 초과 169건을 기록했다. RPM 30에서는 이 호스트의 입력 드롭이 멈췄지만 시작 점검 기한이 만료됐다. 최종 RPM 31은 EL10과 EL9에 순차 적용했다. 두 중앙 작업 모두 성공했고, 업데이터가 두 호스트의 재시작 후 Tetragon 수집을 검증했다. 각 호스트에서 추가로 70초 동안 새 이벤트가 계속 저장됐고 입력 드롭, 파싱 오류와 중앙 전송 손실은 0건이었다. EL9에서는 데몬 초기화부터 로컬 API 준비까지 약 46ms였고, 프로세스 정리 커서가 실제로 전진했다. 이 값은 해당 배포 시점의 측정이다.
