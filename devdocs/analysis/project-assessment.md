# Xe-AntiShell 탐지 범위와 개발 우선순위

2026-11-18 기준. 에이전트 저장소의 `b765e8a`와 배포 설정을 검토했다. 직전 에이전트 릴리스는 RPM28이고 루트 모듈은 공유 프로토콜 v0.3.1을 사용한다. 중앙 서버는 별도 저장소이므로 여기서는 에이전트가 주고받고 검증하는 계약까지 다룬다. [프로젝트 구조](../../Project_tree.md) · [모듈 버전](../../go.mod)

## 개발 우선순위

1. **수집 중단 복구.** 후속 작업에서 Tetragon 자동 재구독과 CLI·패널 공백 표시를 구현했다. 재구독 후 SQLite에 새 이벤트가 커밋되면 복구 시각을 기록한다. 운영 커널에서의 실측은 후속 검증 대상이다. [설계와 검증 범위](../plans/collector-recovery.md)
2. **규칙 관리.** 운영자가 호스트별로 어떤 규칙이 켜졌고 필요한 센서가 실제로 동작하는지 확인할 수 있게 한다. 첫 작업은 기존 14개 규칙의 목록·화면·이력 검색을 일치시키는 것이다.
3. **파일·네트워크 탐지 확장.** 현재 단계는 관측이다. 정상 배포·업로드·외부 API 호출을 표본으로 파일 쓰기 결과, TCP 연결 시도 결과, 서비스 귀속을 확인한다. 이 표본으로 정상 작업과 구분할 수 있는 보호 경로 쓰기를 첫 경보 후보로 검토한다.
4. **저장·전송 여력 확보.** 지금부터 호스트별 일일 저장량과 중앙 전송 대기량을 측정한다. 수집 범위를 넓힐 때 중앙 단절 중 쌓인 데이터가 복구 후 얼마나 빨리 전달되는지, 그동안 손실이 있었는지 비교한다.

후속 구현으로 2번은 CLI·패널·이력에 공통 카탈로그를 연결했고, 3번은 서비스별 표본 조회와 보호 경로 쓰기 후보 검토를 추가했다. 4번은 일일 저장량과 단절·ACK·소진 시간을 측정하고 기존 heartbeat로 보고한다. 아래 운영 문제 표는 분석 기준 커밋에서 확인한 동작이다. [구현과 검증](../plans/operator-rules-observations-capacity.md)

구조적으로 재사용할 부분은 이벤트 처리 단위다. 에이전트는 입력을 정규화한 뒤 하나의 정책 스냅샷으로 보존 여부·탐지·대응을 판단한다. 관리형 모드에서 증거·경보와 중앙 전송분 또는 한도 초과 손실 기록을 한 SQLite 트랜잭션에 담고, 중앙 ACK 이후 전송 대기열을 정리한다. 새 규칙도 같은 경로를 쓰면 이력과 중앙 보고가 일치하는지 기존 테스트로 확인할 수 있다. [처리 순서](../../internal/agent/processing.go) · [증거 저장](../../internal/storage/observations.go) · [전송과 ACK](../../internal/storage/managed.go)

기존 기능 보고서는 RPM24 시점의 기록이다. 이후 RPM27에서 Rocky 9·10 두 호스트의 실제 자격 증명 수신과 Rocky 9 한 호스트의 root 복귀 경보가 중앙까지 전달된 사례가 기록돼 있다. 독립적인 Capability 증가의 운영 검증과 전체 권한 탐지율은 여전히 별개다. 확장 비용에 대한 기존 기준점도 있다. RPM28 합성 시험은 1 vCPU·1 GiB 제한, 초당 원시 입력 400건에서 에이전트 CPU를 한 코어의 66.90%에서 44.18%로 줄였다. 20분 시험에서는 최종 대기·손실이 0이었으나 실제 Tetragon/BPF는 제외됐다. 파일·네트워크 센서를 추가한 호스트의 CPU, 메모리, 하루 DB 증가량은 별도로 측정해야 한다. [측정 조건과 결과](../plans/agent-hot-path-optimization.md)

## 규칙 관리를 만드는 순서

현재는 로컬 YAML 또는 서명된 중앙 정책으로 탐지 활성화, 웹 출처, 셸, 출처·셸 예외, 확장·권한 프로필을 설정한다. 에이전트는 서명·대상·리비전·수집 조건을 확인하고 정책을 저장한 뒤 실행 중 탐지기를 교체한다. 경보에는 규칙 ID·버전과 관리형 정책 리비전이 남는다. 에이전트 DB에는 최신 승인 정책 한 개가 남고, 낮은 리비전과 내용이 다른 동일 리비전은 거절된다. [정책 계약](../../protocol/managed/policy.go) · [적용 경로](../../internal/agent/managed_policy.go) · [저장 경로](../../internal/storage/managed.go)

1. **유효 규칙 목록과 검색을 일치시킨다.** 현재 엔진의 고유 규칙 ID는 14개다. 화면에는 14개 모두 제목이 있지만, 이력 검색의 SQL 제목 매핑과 일치하는 것은 7개였다. 임시 스크립트 1개와 권한 6개는 표시 제목 그대로 검색할 때 누락될 수 있다. 규칙 ID·버전·한글 제목·입력 이벤트·필수 필드·센서·대응 가능 여부를 한 곳에서 정의한다. CLI와 패널에서 규칙별 활성화 여부, 실제 센서 수신 시각, 비활성 사유를 보여준다. [검색](../../internal/storage/history.go) · [웹 규칙 표시](../../internal/webpanel/assets/presentation.js) · [권한 규칙 표시](../../internal/webpanel/assets/privilege.js)
2. **배포 전에 결과 차이를 보여준다.** 제공되는 Tetragon 예제의 셸 수집 목록은 6개이고 프로토콜 기본 정책은 10개를 요구한다. 두 설정을 조합하면 현재 적용 검사가 정책을 거절한다. 현행·후보 정책을 같은 비식별 입력으로 재생해 호스트별 호환성, 추가·감소 경보, 영향을 받는 서비스, 대응 가능 여부의 변화를 보여줄 수 있다. 보관된 입력으로 평가할 수 없는 규칙은 미평가로 표시한다. [예제 설정](../../configs/examples/agent-tetragon.yaml) · [호환성 검사](../../internal/agent/managed_policy.go) · [기존 재생 도구](../../scripts/check-detection.py)
3. **개별 규칙과 예외에 수명을 둔다.** 우선 내장 규칙 ID를 선택하게 하고 예외에는 서비스·규칙·사유·만료를 기록한다. 운영자가 정상·의심·판단 보류와 근거 이벤트를 남기면 다음 정책 비교에서 같은 사례를 재평가할 수 있다. 초기에는 기존 프로필을 규칙 기본값의 묶음으로 유지한다. 서명 필드 확장은 구버전 정책 fixture, 에이전트 지원 버전, 중앙 발행 순서까지 검증한다. [현재 정책 필드](../../protocol/managed/policy.go) · [기존 호환성 시험](../../protocol/managed/policy_test.go) · [기존 정책 설계](../plans/security-policy-and-monitoring.md)
4. **정책을 시험 배포하고 되돌리는 과정을 추적한다.** 소수 호스트에서 원하는 리비전과 적용 리비전, 거절 사유, 규칙별 경보량, CPU·저장량을 비교한 뒤 확대한다. 되돌릴 때는 이전 내용을 더 높은 리비전으로 서명한다. 과거 정책 조회·승인·배포 화면은 별도 중앙 프로젝트의 구현을 확인해 연결한다. [적용 상태](../../internal/agent/managed_policy.go) · [리비전 보호](../../internal/storage/managed.go)

| 첫 규칙 | 서비스별로 쓰기가 허용된 업로드·캐시 경로와 보호할 코드 경로를 정한다. 웹 워커가 보호 경로에 실제 바이트를 쓴 시점에 경보를 낸다. 이어 같은 부팅·관련 계보에서 해당 경로의 실행 파일이 실행되면 두 이벤트를 연결한다. 기존 워커가 스크립트를 해석하는 경우에도 쓰기 경보는 독립적으로 남는다. | 정상 배포·업로드·캐시 생성, 실패한 쓰기, 다른 서비스의 실행, 중복·역순 도착을 대조한다. 경로 일치는 두 관측 사이의 근거로 기록하고 파일 내용 동일성은 미확인으로 둔다. 인터프리터 인자에 위치 분류만 남은 경우에는 동일 파일 실행 여부도 미확인이다. 상관 규칙은 우선 탐지 전용으로 시작한다. 호스트·부팅·실행 식별자, 유한한 시간창과 메모리 한도, 재시작·재전송·정책 전환 시 중복 처리 기준을 정해야 한다. 기존 저장소는 여러 증거 ID를 연결할 수 있지만 관리형 전송은 새 이벤트가 처음 삽입될 때 묶음을 만든다. 따라서 뒤늦게 완성된 경보까지 중앙에 한 번만 도달하는지를 별도로 검증해야 한다. [증거 연결](../../internal/storage/findings.go) · [전송 생성 조건](../../internal/storage/observations.go)

## 이번 검증과 남은 측정

- Go 1.22.0에서 `make test`와 `make vet`를 실행해 에이전트·공유 프로토콜 모두 통과했다. 운영 바이너리 4개를 임시 디렉터리에 새로 빌드했고, 기존 재생 검증 20건(경보 기대 9건, 정상·불확실 11건)과 Tetragon 패키징 Python 시험 68건도 통과했다. [검증 진입점](../../Makefile) · [재생 데이터](../../testdata/events/webshell-process-scenarios.json)
- 검색 매핑은 엔진의 고유 ID, 웹 화면 제목, 메모리 SQLite에서 실행한 실제 SQL 제목 식을 비교했다. 수집 중단 복구와 역순 PID 귀속은 현재 코드 경로를 검토한 결과다.
- 운영 호스트·중앙 배포·실제 커널 부하를 이번에 재검증하지 않았다. 다음 확대 여부는 정상 서비스별 일일 경보량·검토 후 오탐 비중, 센서별 공백 시간, 저장·전송 손실, CPU·RSS·DB 증가량으로 판단한다. 재생 통과 건수로 운영 탐지율을 산출할 수는 없다.
